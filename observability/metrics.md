# Metric (метрика) - числовое измерение определённого свойства системы, привязанное ко времени.

Последовательность измерений образует **Time Series (временной ряд)**.
**Временной ряд** — последовательность значений во времени для одного имени метрики и конкретного набора значений labels.

В модели Prometheus временной ряд определяется именем метрики и конкретным набором значений labels и содержит последовательность значений во времени.

Например, значения CPU для двух разных серверов — два ряда, а не один.

Например:

```text
10:00:00  CPU = 45%
10:00:15  CPU = 52%
10:00:30  CPU = 78%
10:00:45  CPU = 91%
```

По такому ряду можно оценивать нагрузку, выявлять аномалии и строить прогнозы.

## Метрики с тегами (Labels)

- **Иерархические имена:**
 
  ```text
  msk.hw.hw3457.filesystem_avail_bytes
  ```

- **Метрики с тегами:**

  ```promql
  filesystem_avail_bytes{
      dc="MSK",
      type="hw",
      node="hw3457"
  }
  ```

Второй подход используется в Prometheus.

Он позволяет фильтровать и агрегировать данные по отдельным характеристикам.

Например:

```promql
filesystem_avail_bytes{dc="MSK"}
```

## Cardinality (кардинальность).

Кардинальность — количество уникальных временных рядов, которые создаёт метрика с различными комбинациями значений labels.

Например:
> У метрики количества HTTP-запросов есть labels instance, method и status.
> При 10 экземплярах приложения, 5 методах и 6 значениях статуса может получиться до 10 × 5 × 6 = 300 временных рядов.
> Фактическое число зависит от реально существующих комбинаций.

Высокая кардинальность увеличивает потребление памяти, дискового пространства и вычислительных ресурсов Prometheus.

Поэтому значения вроде `user_id`, `request_id` и `trace_id` обычно не следует использовать в labels метрик.


## Типы метрик Prometheus

| Тип           | Назначение                                            | Пример                         |
|---------------|-------------------------------------------------------|--------------------------------|
| **Counter**   | Накопление количества событий                         | Число HTTP-запросов            |
| **Gauge**     | Измерение текущего значения                           | Количество активных соединений |
| **Histogram** | Распределение наблюдений по диапазонам                | Время выполнения запросов      |
| **Summary**   | Статистика наблюдений, включая настраиваемые квантили | p95 времени ответа             |

Классическая Histogram использует buckets, а Summary может вычислять квантили на стороне приложения.
Кроме того, современные версии Prometheus поддерживают Native Histograms.

### Counter

**Counter — счётчик, который увеличивается или остаётся неизменным, пока не произойдёт сброс.**

Пример:

```text
http_requests_total = 100
http_requests_total = 125
http_requests_total = 180
```

После перезапуска приложения счётчик может сброситься.

Для анализа используется функция:

```promql
rate(http_requests_total[5m])
```

Она показывает среднюю скорость увеличения счётчика за последние пять минут с учётом возможных сбросов.

### Gauge

**Gauge — метрика, которая может увеличиваться и уменьшаться.**

Примеры:

```text
memory_usage_bytes
active_connections
queue_length
```

Gauge полезен для измерения текущего состояния системы.

### Histogram

**Histogram — метрика, позволяющая анализировать распределение наблюдаемых значений.**

Особенно полезна для измерения latency.

Например, с её помощью можно рассчитать p95:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

Этот пример относится к классическим Histogram в Prometheus.
Он вычисляет общий приблизительный p95 по всем выбранным рядам.
Для отдельного сервиса или операции нужны фильтры либо сохранение соответствующих labels при агрегации.
Точность оценки зависит от границ buckets.

**p95 — 95-й перцентиль**: примерно 95% наблюдений не превышают это значение.
Для классической Histogram результат является оценкой.

---

**Counter и рестарты.** Небольшое значение Counter само по себе не свидетельствует о перезапуске. Для обнаружения рестартов лучше использовать специализированные метрики, например `process_start_time_seconds` или `kube_pod_container_status_restarts_total`.

**Частота изменения Gauge.** Утверждение, что метрика должна изменяться медленно, не является общим правилом. Gauge может меняться очень быстро. Важно подобрать подходящий интервал сбора данных, чтобы не пропускать существенные изменения.

**Histogram и Summary.** Для агрегации latency между несколькими экземплярами приложения обычно удобнее Histogram. Усреднять готовые p95 отдельных экземпляров математически некорректно.
